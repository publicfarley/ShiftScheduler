● CLI Manual

shift-scheduler

A macOS command-line companion to the ShiftScheduler iOS app — for the person running it by hand, and for the agent running it unattended.

$ shift-scheduler --help v0.1.0
swift-argument-parser JSON on --json, human tables by default EventKit + local JSON persistence

Installation & build

# from the repo root
swift build -c release
.build/release/shift-scheduler --help

# iterate during development
swift run shift-scheduler today

# optional: put it on PATH
cp .build/release/shift-scheduler /usr/local/bin/

Quick start

# one-time: grant Calendar access
shift-scheduler auth request

# set up a location and a shift type
shift-scheduler locations add --name "Downtown" --address "123 Main St"
shift-scheduler types add --title "Day Shift" --symbol D \
  --location "Downtown" --start 07:00 --end 15:00

# schedule and inspect
shift-scheduler schedule add --date tomorrow --type "Day Shift"
shift-scheduler today
shift-scheduler schedule list --from today --to +14d

Global options

Every leaf command accepts these two flags. (schedule, types, locations, log, profile, and auth are group headers — the flags live on their subcommands.)

FlagDescription
--jsonMachine-readable JSON instead of a table/message — on both success and error output. Errors go to stderr.
--data-dir <path>Override the data directory (default ~/Documents/ShiftSchedulerData). Accepts ~. Useful for tests, alternate profiles, or sandboxing an agent's writes.

Root-level: shift-scheduler --version, shift-scheduler --help.

Exit codes

Documented in root --help and stable across releases. Scripts and agents should branch on this first, then read stderr for detail.

CodeMeaning
0Success.
1Runtime failure — not found, not authorized, I/O error, validation error, cancelled, confirmation required without a TTY.
64Usage error — unknown command/subcommand, bad or missing arguments.

Command reference

shift-scheduler today

Show today's scheduled shifts. Requires calendar authorization. Prints a table, or a "no shifts" message if the day is empty.

shift-scheduler today [--json] [--data-dir <path>]

shift-scheduler schedule

Manage scheduled shifts in the calendar. Default subcommand: list.

schedule list

Defaults to the current calendar month. --to is inclusive. Date arguments are validated before the calendar-authorization check, so a bad date reports as a date error, not an auth error.

shift-scheduler schedule list [--from <date>] [--to <date>] [--json]

$ shift-scheduler schedule list --from today --to +14d

schedule add

Creates a calendar event and records an undoable change-log entry. Prints the new EventKit identifier — capture it for later edit/delete/switch calls.

shift-scheduler schedule add --date <date> --type <ref> [--notes <text>] [--json]

$ shift-scheduler schedule add --date 2026-07-15 --type D --notes "Covering for Sam"

schedule edit

Replaces a shift's notes (--notes "" clears them). To change the shift type, use switch instead.

shift-scheduler schedule edit --event-id <id> --notes <text> [--json]

schedule delete

Deletes the shift and records an undoable change-log entry. Prompts for confirmation unless --force — without a TTY, omitting --force fails fast rather than hanging.

shift-scheduler schedule delete --event-id <id> [--reason <text>] [--force] [--json]

schedule switch

Switches a scheduled shift to a different shift type, recording a before/after snapshot so it can be undone.

shift-scheduler schedule switch --event-id <id> --to <ref> [--reason <text>] [--json]

$ shift-scheduler schedule switch --event-id <ID> --to N --reason "Traded with Alex"

shift-scheduler types

Manage shift type templates (title, symbol, time range or all-day, location). Default subcommand: list.

types add

Provide either --all-day or both --start and --end. Overnight shifts (end before start) are supported.

shift-scheduler types add --title <text> --symbol <text> --location <ref> \
  [--description <text>] (--all-day | --start <HH:MM> --end <HH:MM>) [--json]

types edit

Only the fields you provide change. Existing calendar events using this type cascade-update when calendar access is authorized.

shift-scheduler types edit --id <ref> [--title …] [--symbol …] [--location …] \
  [(--all-day | --start <HH:MM> --end <HH:MM>)] [--json]

types delete

Already-scheduled events using this type keep their event but display as "(unknown type)" afterward — deletion does not cascade to the calendar.

shift-scheduler types delete --id <ref> [--force] [--json]

shift-scheduler locations

Manage locations. Default subcommand: list.

locations add

shift-scheduler locations add --name <text> --address <text> [--json]

locations edit

Cascades: shift types referencing this location update automatically, and their calendar events update when authorized. Reports both cascade counts.

shift-scheduler locations edit --id <ref> [--name …] [--address …] [--json]

locations delete

Guardrail

Fails with a locationInUse error if any shift type still references the location. Edit or delete those shift types first, or point them elsewhere.

shift-scheduler locations delete --id <ref> [--force] [--json]

shift-scheduler log

View or purge the shift change log — the audit trail behind undo/redo. Default subcommand: list.

shift-scheduler log list [--limit <n>] [--json]     # newest first, default limit 20
shift-scheduler log purge --older-than <days> [--force] [--json]

shift-scheduler profile

View or update the local user profile. Default subcommand: show. At least one field is required for set.

shift-scheduler profile show [--json]
shift-scheduler profile set [--name <text>] [--retention <policy>] [--auto-purge <true|false>] [--json]

Valid --retention values: 30_days, 90_days, 6_months, 1_year, 2_years, forever.

shift-scheduler auth

Check or request calendar (EventKit) authorization. Default subcommand: status.

shift-scheduler auth status [--json]    # never prompts — reports {"authorized": true|false}
shift-scheduler auth request [--json]   # shows the macOS permission dialog; exits 1 if denied

shift-scheduler undo / redo

Reverts or re-applies the most recent schedule add / delete / switch, from change-log snapshots. Reports nothingToUndo / nothingToRedo when the stack is empty — checked before calendar authorization, so an empty stack is reported accurately even without calendar access.

shift-scheduler undo [--json]
shift-scheduler redo [--json]

Date & time formats

Dates (--date, --from, --to):

InputMeaning
today / tomorrow / yesterdayRelative to the current day.
+Nd / -NdN days from today, e.g. +14d, -7d.
+Nw / -NwN weeks from today, e.g. +2w.
YYYY-MM-DDAbsolute date, e.g. 2026-07-15.

Times (--start, --end): 24-hour HH:MM, e.g. 07:00, 22:30. Overnight ranges (end < start) are valid.

Referencing objects

Anywhere a command takes a shift-type or location reference (--type, --to, --location, or --id on types/locations), pass:

UUID

Always unambiguous — preferred for scripts and agents.

Title / name

Case-insensitive; shift types by title, locations by name.

Symbol

Shift types only, case-insensitive (e.g. D, N).

A match on more than one object fails with an ambiguous error listing the candidates — re-run with the UUID. Scheduled shifts are always referenced by EventKit --event-id, obtained from schedule list or the output of schedule add.

For LLM agents machine contract

Rely on this contract rather than parsing human-readable text.

01 · Always pass --json

Human table output isn't a stable format; JSON field names are.

02 · Error shape (stderr)

{
  "error": {
    "message": "No shift type matches 'Nite Shift'",
    "suggestion": "Run 'shift-scheduler types list' to see available shift types. …"
  }
}

suggestion appears when there's an actionable next step. Check the exit code first — 0 means stdout holds the result; nonzero means stderr holds the error.

03 · Destructive commands never hang

schedule delete, types delete, locations delete, and log purge only prompt when stdin is a TTY. Non-interactively, the prompt is skipped and the command fails immediately with confirmationRequired (exit 1) unless --force is passed. Always pass --force from an agent, and gate that decision in your own logic.

04 · auth request needs a human

It shows the native macOS permission dialog — there's no headless path to grant EventKit access. Call auth status --json first; if authorized is false, surface that to a human instead of invoking auth request unattended.

05 · Prefer UUIDs

Avoid ambiguous errors in generated commands. Get UUIDs from id in types list --json / locations list --json; get event IDs from eventId in schedule list --json / schedule add --json.

06 · No idempotency on add

schedule add always creates a new event — retrying a successful call duplicates the shift. Check schedule list first if you're unsure whether it already exists.

07 · --data-dir sandboxes reference data only

It does not sandbox calendar writes — those always go to the shared functioncraft.ShiftScheduler calendar. There's no --dry-run for calendar-mutating commands; confirm authorization and review schedule list before mutating if you need a rehearsal.

08 · undo/redo is one global, shared stack

Not scoped per session or per actor. Undoing after another actor (the iOS app, another script) has made changes may not do what you expect — prefer targeted edit/switch/delete calls with explicit event IDs in multi-actor environments.

Stable JSON fields

ChangeLogEntryDTOid, timestamp, user, changeType, shiftDate, from, to, reason

Dates are YYYY-MM-DD; timestamps are ISO 8601.

Minimal agent recipe

shift-scheduler auth status --json                            # confirm access first
shift-scheduler types list --json                              # get type UUIDs
shift-scheduler locations list --json                           # get location UUIDs
shift-scheduler schedule list --from today --to +7d --json     # check current state
shift-scheduler schedule add --date 2026-07-15 --type <UUID> --json   # mutate

For human users

  • Run any command with --help for its flags, an abstract, and worked examples — every leaf command has an EXAMPLES: section, e.g. shift-scheduler schedule switch --help.
  • Omit --json for readable, aligned tables.
  • Destructive commands prompt [y/N] interactively — no need to remember --force unless you're scripting.
  • Made a mistake? shift-scheduler undo reverts the last add/delete/switch; redo re-applies it.
  • The calendar is named functioncraft.ShiftScheduler, visible in Calendar.app and the iOS app once access is granted and iCloud sync catches up.
  • --data-dir is mainly for testing — leave it at the default day-to-day so the CLI and iOS app see the same reference data.

Data model notes

Reference data (shift types, locations, profile, change log) is local JSON on the machine running the CLI, at ~/Documents/ShiftSchedulerData/ by default. It syncs through CloudKit only where entitlements allow (the iOS app) — an unbundled CLI binary has none, so CloudKit sync silently no-ops there (treated internally as a benign "offline" condition), and reference data stays local to that machine's --data-dir.

Scheduled shifts live in EventKit, in the shared functioncraft.ShiftScheduler calendar. This does sync across devices via iCloud, independent of the CloudKit path above — it's the actual mechanism by which CLI-created shifts appear in the iOS app.

Undo/redo replays from ChangeLogEntry snapshots (no stored EventKit identifiers); shifts are re-located by date + shift-type ID when reverting or reapplying.
