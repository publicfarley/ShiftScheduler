Part 1

One-time setup

1

Confirm your account

  • You need a paid Apple Developer Program membership under team M8T74C3QWG.
  • In Xcode, open Settings → Accounts and confirm your Apple ID is signed in. The script uses it unless you set up an API key in step 2.
2

Create an API key

Optional

A key lets the script sign and upload without depending on Xcode's login session.

  1. Open App Store Connect → Users and Access → Integrations.
  2. Generate a Team Key with the App Manager role.
  3. Download the .p8 file. Apple lets you download it only once.
  4. Note the Key ID and the Issuer ID shown on that page.
mkdir -p ~/.appstoreconnect/private_keys
mv ~/Downloads/AuthKey_ABC123DEFG.p8 ~/.appstoreconnect/private_keys/
chmod 600 ~/.appstoreconnect/private_keys/AuthKey_ABC123DEFG.p8

Add the three variables to ~/.zshrc. Set all three or none.

export ASC_KEY_ID=ABC123DEFG
export ASC_ISSUER_ID=00000000-0000-0000-0000-000000000000
export ASC_KEY_PATH=$HOME/.appstoreconnect/private_keys/AuthKey_ABC123DEFG.p8
3

Dry run the archive

This builds and exports an .ipa without uploading anything. With automatic signing it also registers the App ID and creates the provisioning profile, which step 4 needs.

scripts/testflight.sh --no-upload --skip-tests

Read the preflight warnings it prints. Two matter for this app:

  • No aps-environment entitlement. Ignore this unless you use CloudKit push subscriptions. If you do, add the Push Notifications capability in Xcode first.
  • No PrivacyInfo.xcprivacy. Apple can flag required-reason API use (for example UserDefaults or file timestamps) after upload. Adding a privacy manifest in Xcode avoids that.
If signing fails with a missing profile or iCloud container error, open the project in Xcode, select the ShiftScheduler target, and check Signing & Capabilities. Confirm the iCloud capability lists the container above, then rerun.
4

Create the app record

  1. Open App Store Connect → Apps and choose + → New App.
  2. Platform iOS. Pick a name and primary language. Choose functioncraft.ShiftScheduler from the Bundle ID list. Enter any SKU.
  3. Save.
Bundle ID missing from the list? The dry run in step 3 did not register it. Rerun it, or register the ID at developer.apple.com under Certificates, Identifiers & Profiles. You cannot change the bundle ID after the record exists. Note that it has no com. prefix, unlike the iCloud container.
5

Deploy the CloudKit schema to Production

TestFlight builds talk to the Production CloudKit environment. Your development schema is not there until you deploy it.

  1. Open the CloudKit Dashboard and select iCloud.com.functioncraft.ShiftScheduler.
  2. In the Development environment, choose Deploy Schema Changes.
  3. Review the record types and confirm the deploy to Production.
Back up first. The Production container starts empty, and an empty CloudKit fetch has wiped local JSON in this project before. Confirm that fix is in place, and export your real shifts with the CLI before installing the first TestFlight build on your own phone.
Part 2

Each release

1

Get main clean

The script warns about uncommitted changes and about branches other than main, but it still builds them. Merge and commit first.

git status
git branch --show-current
2

Bump the version if needed

The build number changes on its own. The marketing version (currently 1.0) does not. Change MARKETING_VERSION in Xcode only when you want testers to see a new version number. Apple requires a new Beta App Review for each new version that goes to external testers.

3

Run the script

scripts/testflight.sh

It runs these stages in order and stops on the first failure:

  1. Preflight: reads settings, checks entitlements, picks the auth method.
  2. Unit tests on the iPhone 17 Pro simulator.
  3. Release archive for a generic iOS device, to build/testflight/.
  4. Export and upload to App Store Connect.
--skip-tests
Skip the test run.
--no-upload
Export an .ipa only.
--build-number N
Use a specific build number instead of the timestamp.
4

Wait for processing

After the upload finishes, App Store Connect processes the build, usually in 5 to 30 minutes. Watch it under your app → TestFlight → Builds. You also get an email when it is ready or if it is rejected.

Part 3

Getting it onto devices

Internal testing No review

  1. In TestFlight, open Internal Testing and create a group.
  2. Add yourself. Internal testers must be users on your App Store Connect team, up to 100.
  3. Add the processed build to the group.
  4. On your iPhone, install the TestFlight app, accept the email invite, and install ShiftScheduler.

External testing Beta App Review

  1. Create an External group. Add testers by email, or enable a public link.
  2. Fill in Test Information: what to test, a contact email, and a note about the calendar permission the app asks for.
  3. Add a build and submit it. The first build of each new version goes to Beta App Review, which often takes a day.
Builds expire after 90 days. Upload a fresh build before then so testers keep access.

Troubleshooting

SymptomLikely cause and fix
Script says tests failedFix them, or rerun with --skip-tests if you accept the risk.
No profile or "no account" signing errorSign in under Xcode Settings → Accounts, or set the three ASC_* variables.
"set all of ASC_KEY_ID, ASC_ISSUER_ID and ASC_KEY_PATH"One or two of the variables are set. Set all three or unset them all.
Upload rejected: build number already usedTwo runs in the same minute. Wait a minute or pass --build-number.
No app record found for the bundle IDCreate the app record (Part 1, step 4) with the exact bundle ID.
Build never appears in TestFlightCheck your email for a processing rejection. Common causes are a missing privacy manifest or entitlement mismatch.
Syncs fine in Xcode, fails in TestFlightCloudKit schema not deployed to Production (Part 1, step 5).
Empty calendar on first launchProduction container starts empty. Grant calendar access, then restore from your backup.
